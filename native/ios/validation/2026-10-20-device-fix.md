# Physical-device startup route handling

An Xcode screenshot of the user's iPhone 17 Pro showed the listener stopped with
“Audio was interrupted or the input changed.” The original observer stopped on
all AVAudioSession route-change notifications, including changes generated by
its own startup configuration. This was not exercised by fixture-only simulator
validation.

The observer now compares the configured input IDs, sample rate, and channel
count against the current session and checks whether the engine is still
running. It keeps capture alive for category/output-only notifications with an
unchanged input. Actual input/format changes, unavailable routes, stopped engines,
interruption beginnings, and media-service resets still stop capture. Rearming
uses a fresh AVAudioEngine. Console metadata reports the route-change reason and
whether capture was stopped, without recording audio.

Validation: signed iPhone Release build succeeded; all seven simulator XCTest
checks passed, including the two new route-change regressions. The updated app
was installed on the connected iPhone. Live device confirmation passed:

```text
WAKE_AUDIO started inputRate=48000.0 inputChannels=1
WAKE_AUDIO route reason=3 inputChanged=false engineRunning=true stopping=false
WAKE_AUDIO detected phrase=HEY_LOBBY prerollFrames=32000
WAKE_AUDIO handoff complete frames=80000
```

The real device emitted category-change reason 3 after startup. The corrected
observer kept the unchanged input running. The user spoke into the actual phone
microphone (not fixture mode), triggering the model and a complete five-second
handoff. This confirms the startup regression and microphone handoff on hardware;
it does not establish prolonged locked-screen reliability or battery behavior.

## Playback volume

The user reported very quiet replay at maximum system volume. Playback was
still using the microphone's measurement-mode session. Replay now stops capture
and configures `.playback` with `.default` mode. Starting listening again stops
replay before rebuilding capture. Original handoff samples remain unchanged.

Physical-device logging confirmed normal mode, Speaker output, and system volume
1.0. The user confirmed that playback volume is now normal. No additional sample
amplification was retained or deployed.
